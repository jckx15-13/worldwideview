## 1. Executive summary

The work divides cleanly in two.

**Phases 39, 40, 42, 43 bought correctness and enforcement, not speed.** The
central finding was that this project's CI safety net existed but was switched
off: `ci.yml` ran both the unit-test gate and the dependency-audit gate with
`|| true`, so neither could ever fail. `next.config.ts` carried
`typescript.ignoreBuildErrors`, so builds shipped without type-checking. Turning
these on required first fixing what they had been hiding.

**Phase 41 bought speed, and it is the only phase that changes what a user
experiences.** The globe's 1.34 MB of compressed JavaScript now begins
downloading **308 ms earlier**, for zero additional bytes.

| Outcome | Before | After |
|---|---|---|
| Build type-checks | no | **yes** |
| CI unit-test gate can fail | no | **yes** |
| CI audit gate can fail | no | **yes** |
| High-severity advisories | 8 | **0** |
| Compressed bundle measurable | no | **1.76 MB / 2 MB budget** |
| Runtime measurable | no | **`pnpm perf`** |
| Globe chunk discovery | 327 ms | **19 ms** |

## 4. Phase 40 — Type-checked builds and CI gates that can fail

### The escape hatch was hiding a real defect

Deleting `typescript.ignoreBuildErrors` from `next.config.ts` surfaced
`.next/types/app/locked/page.ts(39,29): error TS2344` — `searchParams` in
`src/app/locked/page.tsx` was typed as a plain object, but Next 15+ makes it a
`Promise`. Fixed by making the page `async` with `Promise<{ reason?: string }>`.

**`tsc --noEmit` returning 0 errors did not predict this.** The blocking error
lived in *generated* route types, which `next build` checks and a bare `tsc` over
source never sees. "tsc is clean" had been false assurance.

The route is reached only by redirect from `src/proxy.ts:189`; no code imports it.

### Test flakiness was two timeout budgets, not one

| Knob | Default | Set to | Why |
|---|---:|---:|---|
| `hookTimeout` | 10,000 ms | **60,000 ms** | a `beforeEach` in `better-auth.test.ts` measured at **40,362 ms** under concurrent load |
| `testTimeout` | 5,000 ms | **30,000 ms** | `transport-spike.test.ts` dynamically imports the MCP SDK inside the test body |

Environment setup dilates under load; test logic does not. These are the two
distinct budgets that dilation crosses.

### The gates

`ci.yml` ran `vitest run --coverage || true` and
`pnpm audit --audit-level high || true`. Neither could fail. Both `|| true`
suffixes removed.

Coverage thresholds of **80/70** had never been met and, because of `|| true`,
had never been seen to fail. Measured actuals over two runs were functions
35.60/35.55%, branches 34.55/34.46%. Ratcheted to **34/33** — roughly 1.5 pp
below actual, enough margin that a loaded CI runner cannot flap the gate while
still blocking real regression. **A gate that flaps is worse than no gate.**
Raise as coverage improves; never lower.

## 5. Phase 41 — Runtime and bundle performance

This phase was blocked for a real reason: the project could not observe its own
runtime. Next 16 removed the per-route First Load JS columns from build output,
and every Playwright config ran `pnpm dev`, whose numbers are unminified,
unsplit and compiled on demand. So every performance claim was inference.
Tooling first, then the fix it revealed.

### 5.1 Measurement tooling added

| Tool | Command | Answers |
|---|---|---|
| `@next/bundle-analyzer` | `pnpm analyze` | Per-module bundle attribution |
| Production perf harness | `pnpm perf` | What a browser downloads, and when |

The harness (`playwright.perf.config.ts` + `tests/perf/globe-load.perf.spec.ts`)
runs `next start` against a real build on port 3005. It needs **no database**:
`src/proxy.ts` gates `/` on session-cookie *presence* only — `hasBetterAuthCookie`
is explicitly documented as not verifying validity — and `src/app/page.tsx` does
no auth of its own, so a synthetic cookie reaches the identical client bundle.
Chunk hashes are read from `.next/react-loadable-manifest.json` rather than
hardcoded, so the spec survives rebuilds.

Next prints `"next start" does not work with "output: standalone"`. That warning
is ignored deliberately: the suggested `node .next/standalone/server.js` serves
no static assets unless `.next/static` and `public/` are copied in by hand, which
would make every chunk 404 and the measurement meaningless.

### 5.2 The diagnosis

`GlobeView` is loaded via `next/dynamic(..., { ssr: false })` at
`src/components/layout/AppShell.tsx:47` and rendered **unconditionally** at
line 181 — no conditional, no tab, no interaction gate. Every visitor downloads
it. But `ssr: false` means it never renders on the server, so Next emits no
preload hint and the prerendered HTML contained **zero** references to its
chunks.

The fetch was therefore serialized: main bundle → hydrate → *then* discover and
fetch. Measured: first JS request at **19 ms**, globe chunks not requested until
**327 ms**. That 308 ms is idle network on the critical path of the component
that *is* the product.

**The obvious fix was the wrong one.** Gating the globe behind a click is not
viable — the globe is the product. The target was the waterfall, not the render.

### 5.3 The fix and its measured effect

`src/app/page.tsx` calls React 19's `preload()` with hrefs resolved by
`src/lib/globe-preload.ts` from the loadable manifest.

| Metric | Before | After | Δ |
|---|---:|---:|---|
| First JS request | 19 ms | 19 ms | — |
| **Globe chunks discovered** | **327 ms** | **19 ms** | **−308 ms** |
| **Idle gap on critical path** | **308 ms** | **1 ms** | **−307 ms** |
| Globe fully downloaded | 754 ms | 185 ms | −569 ms |
| Globe chunks in HTML | 0 of 6 | **6 of 6** | fixed |
| `rel="preload"` links | 2 | 8 | +6 |
| Globe chunk requests | 6 | **6** | no double fetch |
| Globe bytes (encoded) | 1,342,901 | **1,342,901** | unchanged |
| Total JS requests | 50 | 50 | unchanged |
| Total JS bytes | 2,073,831 | 2,073,831 | unchanged |

**The fix ships zero additional bytes.** It is purely a scheduling change.

It is scoped to `/`, deliberately not `layout.tsx` — `/login`, `/setup` and
`/locked` share that layout and must not pull 1.34 MB of Cesium.

Failure is silent and total by design: any problem reading the manifest yields
`[]`, restoring exactly the pre-existing behaviour. A missing preload is a
slower page; a throwing root route is an outage.

### 5.4 Two failure modes checked, not assumed

1. **Double fetch.** A preload whose URL or credentials mode does not match the
   later `<script>` tag makes the browser download twice. Chunk request count
   stayed at 6 and encoded bytes are byte-identical, so the preload is reused.
2. **Clean builds.** `/` is prerendered at build time, so if the manifest were
   not written before prerendering the preload would silently do nothing — in
   Docker, where every build is clean, which is exactly where it matters.
   Verified by deleting `.next` (preserving `.next/cache`, as `Dockerfile:81`
   mounts it) and rebuilding: **6 of 6** chunks present in
   `.next/server/app/index.html`, 8 preload links, measured gap **0 ms**.

### 5.5 `experimental.cpus` — decided, stays at 2

- `Dockerfile:81` builds with `--max_old_space_size=3072` — **half** the local
  6144, against a measured 3,575 MB peak build RSS.
- `Dockerfile:96` sets runtime `--max-old-space-size=768`.

The original justification for `cpus: 2` (OOM mitigation) was refuted, but the
setting turns out to be right for a different reason. More parallel webpack
workers means more concurrent heap against a 3072 MB ceiling. Build wall-clock is
a developer cost, not a user one; trading a container OOM for it is a bad deal.
Revisit only alongside raising that cap, and validate in Docker.

### 5.6 Caveats on these numbers

- **Localhost, not a real network.** The 308 ms gap is hydration-bound and
  survives any connection, but the 569 ms download saving is a floor locally and
  grows on slower links, where 1.34 MB takes real time.
- **`appReadyMs` is unmeasured (`null`).** The boot sequence never completes in
  the harness because no Redis, Postgres or data engine is running, so plugins
  never load. The waterfall metrics do not depend on boot completing. Wiring
  backends in would make time-to-interactive measurable — the obvious next
  increment.
- **Per-route First Load JS is still not emitted by Next 16.** `pnpm analyze`
  supersedes it for attribution.

## 6. Phase 42 — Security

### Dependency advisories: 8 high → 0

| Package | Resolution |
|---|---|
| `brace-expansion` | `pnpm.overrides` → `^5.0.8` |
| `fast-uri` | existing override was **stale** (`<3.1.2`); corrected to `^3.1.5` |
| `nanoid` | `pnpm.overrides` → `^3.3.18` |
| `extract-zip` | no patched version; removed with `@size-limit/preset-app` |

The `extract-zip` advisory was unpatchable, pulled in transitively by
`@size-limit/preset-app`'s Chrome-based `time` plugin — which was never used.
Swapping to `@size-limit/file` removed the advisory **and** fixed `size-limit`,
which had been failing locally with `undefined: command not found`. That
produced the project's first real compressed-bundle figure: **1.76 MB brotlied**
against a 2 MB budget.

### The diagnostics client was lying about sanitizing

`packages/wwv-diagnostics-client` stamped every payload `sanitized: true` while
redacting only 6 exact key names with no recursion. `apiKey`, `accessToken`,
`authorization`, `cookie`, `privateKey` and `jwt` all shipped in clear.

Rewritten with the public API (`reportToDiagnosticEngine`, `DiagnosticReport`)
unchanged:

- **Substring matching** across 11 patterns, not exact-key equality.
- **Recursion** into nested objects and arrays, depth-bounded at 6 so cycles
  truncate rather than hang.
- **String-level redaction** of bearer/basic tokens and credential-shaped query
  params.
- **Scheme validation** on the destination URL — `http:`/`https:` only. On the
  browser side the endpoint comes from mutable global state, so without this any
  script able to set `window.ENV` could redirect every future report, stack
  traces included, to a host of its choosing.
- **Working backoff.** `fetch` resolves on 4xx/5xx, so a dead engine was
  hammered forever because the backoff never armed. `res.ok` is now checked
  explicitly, `sendBeacon`'s `false` return is no longer discarded, and requests
  are bounded by `AbortSignal.timeout(5000)`.

Covered by 11 new tests. The suite default is jsdom, which defines `window` and
steers execution down the `sendBeacon` branch; the spec pins the server path with
a `// @vitest-environment node` docblock.

**Note:** nothing in the repository ever assigns `window.ENV`, verified by
repo-wide grep. Until something does, the browser branch no-ops. Wiring it up is
a deliberate decision, not an oversight to fix casually.

## 7. Corrections ledger

Eight claims recorded as fact turned out to be wrong. This list is the reason
this report exists.

| Claimed | Actual | How it was caught |
|---|---|---|
| Peak build RSS 8,339 MB | **3,575 MB** | measuring script summed unrelated host PIDs |
| `cpus: 2` is OOM mitigation | premise false — build never neared the cap | corrected RSS measurement |
| Merge base `fec442f7` | **`556acd17`** | conflict estimates were inflated |
| `tsc --noEmit` clean ⇒ build safe | false — error was in *generated* types | deleting `ignoreBuildErrors` |
| Missing size columns = non-TTY output | false — Next 16 removed them | build under `script -qec`, real pty, exit 0, still 0 columns |
| `transport-spike` fails on `hookTimeout` | fails on **`testTimeout`** | reading the actual failure |
| Removing `\|\| true` is near-zero risk | would have red-lined CI on **coverage**, not tests | running the exact CI command |
| Cesium is "lazy" | code-split but **unconditional** — deferred, not on-demand | reading `AppShell.tsx:181` |

The last one is worth dwelling on. It began as a menu selection presented to the
user, whose answer was then written into a diagram with a green checkmark and
used to rebuild the phase plan — without measurement. When measured, it was half
right, and the half that was wrong *reversed* the conclusion: Cesium went from
"already handled" back to the top optimization target. A related architecture
diagram produced in the same period contains fabricated figures and a "Click Map"
step that does not exist in the codebase; it should be regenerated or discarded.

## 8. External code-audit resolution

An audit report covering the sibling `silver-wolf-vi` project was assessed
against the source. **Two of eight dependency recommendations survived
verification; three would have broken the build.**

| Recommendation | Verdict | Evidence |
|---|---|---|
| `@prisma/client` missing → "build will fail" | **False** | `src/lib/prismaClient.ts:7` requires it in a try/catch with a documented JSON-storage fallback; installing it switches storage backends |
| Remove `@wwtelescope/*` | **Correct** | zero source imports |
| Remove `tailwindcss` "clearly dead" | **Breaks build** | `vite.config.ts:1,89` + `src/index.css:2` `@import "tailwindcss"` |
| Remove `autoprefixer` | **Correct** | appears nowhere but package.json |
| Remove 6 `@storybook/*` | **Breaks** | `.storybook/main.ts` + two live scripts |
| Remove `@chromatic-com/storybook` | **Breaks** | registered addon |
| Remove `playwright` | **Breaks** | backs Storybook browser tests via `@storybook/addon-vitest` |

The tailwind recommendation was the report's own "start here, clearly dead"
advice. Its reasoning — "not in postcss.config" — is a Tailwind **v3**
assumption; the project is on v4, which uses a Vite plugin and a CSS `@import`
and never has a postcss.config.

Applied in `42350b71`: the two correct removals, plus deletion of the
`wwv` manualChunks group in `vite.config.ts:169` that the report never
mentioned and which would have pointed Rollup at uninstalled modules.
Verified `vite build` exit 0, `tsc --noEmit` exit 0.

**Three real problems the audit missed:** two lockfiles coexisting
(`package-lock.json` and `pnpm-lock.yaml`, making installs nondeterministic);
`"latest"` version specifiers on `playwright` and `@chromatic-com/storybook`;
and the absence of any knip config, which *is* the "274 unused files" finding —
knip scanned `odysseus/`, `bridge/`, `dist/` and `scripts/` with zero exclusions.
That number measures missing configuration, not dead code.

The audit's separate WWV-monorepo claims were **not** verified beyond one spot
check (`server-only` imported at `worldwideview-web/src/lib/supabase/admin.ts:3`
but undeclared — real). Given the first report was wrong on six of eight
checkable items, its remaining numbers deserve the same treatment before anyone
acts on them.

again. The first red build after this work is expected and correct, not a bug.
